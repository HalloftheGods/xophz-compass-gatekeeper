and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Changed (License products)
- **License products (#1552)**: Gatekeeper is now a license engine other plugins register into, and the XP Pro code moves out of its specifics. A plugin adds a product with the `gatekeeper_license_products` filter (label, key prefix, option prefix, account and device field names, device cap, grace and trial, plans callable, checkout product, webhook and setup option names, route prefix, a settings schema and the email strings); `Gatekeeper_License_Products` validates it, fills the defaults, and logs and skips a malformed one. The engine classes are `Gatekeeper_License_Store`, `Gatekeeper_License_Db`, `Gatekeeper_License_Stripe`, `Gatekeeper_License_RevenueCat`, `Gatekeeper_License_Intake`, `Gatekeeper_License_REST` and `Gatekeeper_License_Setup`, all taking the product; consumers call `gatekeeper_license_record()`, `gatekeeper_license_entitled()`, `gatekeeper_license_for_key()`, `gatekeeper_counter_bump()` and `gatekeeper_rate_limited()` behind `function_exists`. `gatekeeper_license_applied` fires after a webhook changes a record and `gatekeeper_license_public_view` filters the JSON a client sees. Records gain `last_event` (id, action, source, time), shown on the admin page.
- **XP Pro keeps its contract**: every `/compass/v1/gatekeeper/xp-pro/*` route keeps its path, parameters, status codes and JSON, and the options (`gk_xp_pro_*`, `gatekeeper_xp_pro_webhooks`, `gatekeeper_xp_pro_stripe_setup`, `xp_pro_ai_daily_limit`, `xp_pro_lifetime_on_sale`) keep their names, so there is no data migration. The product itself, its plans, strings and the Gemini AI proxy (`POST /xp-pro/ai`) are now registered by `xophz-compass-xp`; Gatekeeper no longer has an AI class. On a site where Gatekeeper updates first, a built-in `xp-pro` product keeps serving (plans through the old `gatekeeper_xp_pro_plans` filter, or the shipped catalog) and logs one line per request until the XP plugin registers it.
- **Admin**: Settings > Gatekeeper XP Pro is now Settings > Gatekeeper Licenses (same `gatekeeper-xp-pro` slug), one section per product, with the settings form drawn from the product's schema (an int row may carry `min` and `max`).
- **To remove next release**: the `Gatekeeper_Xp_Pro_Licenses` facade (get, is_entitled, find_by_key, public_view and the old constants), the `Gatekeeper_Xp_Pro_Db` alias, the built-in transition `xp-pro` product and the `gatekeeper_xp_pro_plans` filter, once the XP plugin that registers the product is out everywhere.
- **Behaviour notes**: the XP plugin's AI route now attaches an unseen device when the key has room (it answered 402 before), answers 409 `device_limit` for a key already on 10 devices, and its daily count lives in a `gk_lic_ctr_` row instead of `gk_xppro_ai_` (the daily cleanup still sweeps the old rows).

### Added (XP Pro, Do It For The XP)
- **License store (#6006)**: `Gatekeeper_License_Store` (the product id first on every method; `Gatekeeper_Xp_Pro_Licenses` is a one-release facade for `xp-pro`) keeps one record per family in `gk_xp_pro_{family_id}` (autoload off) with lookup options for the key (`XP-PRO-XXXX-XXXX-XXXX`), Stripe subscription, payment intent and customer ids, and the purchase email. Idempotent grants, a lifetime plan that later subscription events never shorten, expire and revoke that keep the record, the 3 day grace window, 10 devices per license and the last 50 event ids. Never touches `compass_gatekeeper_licenses`.
- **Stripe and RevenueCat adapters (#6007, #6008)**: `Gatekeeper_License_Stripe` and `Gatekeeper_License_RevenueCat` (`to_op( $payload, $product )`) turn each event into one license operation (pure, tested row by row with real-shaped fixtures). A full refund of a subscription charge revokes by customer when the charge's payment intent was never stored.
- **Hookshot intake and admin (#6009)**: `Gatekeeper_License_Intake` handles `xophz_hookshot_incoming` only for the webhook ids in a product's `webhooks_option` (`gatekeeper_xp_pro_webhooks` for XP Pro) and only when `Hookshot_Signature::was_verified()`; the id picks the adapter. A new key is emailed once. Settings > Gatekeeper Licenses (slug `gatekeeper-xp-pro`) holds, per product, the webhook ids, the settings from its schema (`xp_pro_ai_daily_limit` for XP Pro) and the license list with Reset devices.
- **REST (#6010)**: `Gatekeeper_License_REST` registers `GET /{route_prefix}/plans`, `POST /{route_prefix}/claim`, `/validate`, `/recover` and `/manage` per product (`/xp-pro/...` for XP Pro, unchanged), public and rate limited per client address (30 a minute, recover 5 an hour).
- **AI helpers proxy (#6012)**: `POST /xp-pro/ai` (served by `Xophz_Compass_Xp_Pro_AI` in the XP plugin since #1552, which checks the key through `gatekeeper_license_for_key()`) replaces the Gemini key that shipped in the Do It For The XP app. It needs an entitled XP Pro license on a registered device (sandbox licenses only where `wp_get_environment_type()` is `local` or `development`), accepts only the tasks `monster_name`, `checklist`, `full_beast` and `schedule` with their structured, length-capped fields (never a prompt), keeps the prompts in PHP, sends the key in the `x-goog-api-key` header with the Google connector's model (fallback `gemini-3.6-flash`), parses each reply to its task's JSON shape (a malformed reply is a 502), and allows 100 calls per license per day (`xp_pro_ai_daily_limit`).
- **Setup API (#6018)**: `POST /xp-pro/setup/stripe-webhook {mode: test|live, rotate?}` (`Gatekeeper_License_Setup`, manage_options, one pair of routes per product) creates an incoming Hookshot webhook, registers it with Stripe for the XP Pro events using Bazaar's Stripe key for that mode, writes Stripe's signing secret straight into the webhook's write-only meta (header `Stripe-Signature`, mode `hmac`), and records the id in `gatekeeper_xp_pro_webhooks` as `stripe_test` or `stripe`. Neither the Stripe key nor the signing secret appears in any response; a repeat call returns the existing setup unless `rotate` is true; a Stripe error removes the half-made webhook. `GET`/`POST /xp-pro/settings` reads and writes the webhook slots, `xp_pro_ai_daily_limit` and `xp_pro_lifetime_on_sale`; the redirect allowlist and the site URL are shown read-only. Intake accepts the `stripe_test` slot beside `stripe`.

### Fixed (XP Pro review)
- **Refunds, sources and env (#6013)**: records track `period_source` (`stripe:<sub id>` or `revenuecat:<product id>`) and, for lifetime, `lifetime_source`. grant and extend keep the later `expires_at`; expire applies only from the current period source; only a refund of the lifetime purchase (or a dispute on it) revokes, any other refund ends the paid period as `expired` (the next `invoice.paid` or RENEWAL reactivates it) and never touches an active lifetime. Production wins: a sandbox event never changes a production record, and a production event on a sandbox record sets it to production. Settings > Gatekeeper XP Pro gains a Restore button (manage_options + nonce) that sets a record active and notes the admin user id and time.
- **Locks and atomic counters (#6014)**: `Gatekeeper_License_Store::apply()`, `attach_device()`, `reset_devices()` and `restore()` run under a per-family MySQL named lock (`GET_LOCK('gk_xp_pro_{family_id}', 10)`, released in a `finally`) and re-read the record after taking it; a lock that cannot be taken in 10 s writes nothing and logs the event id. The AI daily cap and the REST rate limits use `Gatekeeper_License_Db` (`Gatekeeper_Xp_Pro_Db` is an alias for one release), one `INSERT ... ON DUPLICATE KEY UPDATE option_value = option_value + 1` per hit on a counter whose name carries its window (unix window start for rate limits, `Ymd` for the daily cap), with an atomic decrement when a Gemini call fails. A daily cron event (`gk_xp_pro_cleanup_counters`) deletes counters older than 2 days.
- **Client address and buckets (#6015)**: XP Pro rate limits and the AI route take the caller's address from `Hookshot_Client_Ip::resolve()` when Hookshot is active, else `REMOTE_ADDR`. Behind Cloudflare the site must define `XOPHZ_HOOKSHOT_TRUSTED_PROXIES` (Cloudflare's published ranges) in `wp-config.php`, otherwise every caller shares Cloudflare's address. `/claim` and `/validate` count per family (the claimed family, or the key's family) plus address, only for families that exist; every other route counts per address.
- **Paid checkouts only (#6016)**: `checkout.session.completed` grants only when `payment_status` is `paid` or `no_payment_required` (an `unpaid` delayed-payment session is none). `checkout.session.async_payment_succeeded` grants like a paid completed session; `checkout.session.async_payment_failed` revokes that purchase by payment intent (subscription for a subscription session) with the refund rules above and never falls back to the customer.

### Added
- `Gatekeeper_REST::guard()` and global `gatekeeper_guard()` helper function providing universal cryptographic token and permission verification across all companion plugins.
- `gatekeeper_route_guard` filter hook for dynamic REST route security registration.
- Hookshot webhook fulfillment listener (`xophz_hookshot_incoming`) for automated machine API key generation (`xp_live_*`) on completed Stripe subscription checkouts.
- Dedicated REST routes for listing and minting client software licenses (`GET /licenses`, `POST /licenses`).
- Dedicated REST route for listing active GitHub sponsor entitlements (`GET /sponsors`).
- Expanded machine OpenAPI abilities declaration for AI coding assistants.
- Unit tests in `tests/` (`node tests/run-tests.mjs`, run against the `u-wordpress` container) for license validation and checkout key ownership.
- `Gatekeeper_Keys::generate_key()` takes an optional `$owner_email`, stored on the key and returned by `list_keys()`.

### Changed
- The route guard moved to `Gatekeeper_Route_Guard` (`includes/class-gatekeeper-route-guard.php`). `Gatekeeper_REST::guard()`, `gatekeeper_guard()` and the `gatekeeper_route_guard` filter keep working and delegate to it.

### Security
- The route guard reads an API key only from the `X-API-Key` header or `Authorization: Bearer`. A key in the query string (`?api_key=`) is refused with 400 `gatekeeper_api_key_in_url`, valid or not, and an `api_key` body field is ignored (#5992). Rotate any key that was ever sent in a URL.
- `POST /licenses/validate` no longer accepts unminted license keys (#5999). The "legacy offline license" fallback, which returned valid for any `CX-` string of 14 or more characters (the VIP tier with unlimited devices if it contained `VIP` or `MASTER`), is removed. License keys are random and carry no signature, so only keys stored in `compass_gatekeeper_licenses` validate. Keys minted only into the Chemical X edge KV store are not in that table and are refused here.
- The preview keys `CX-DEV-PREVIEW` and `QUANTUM-VIP` unlock the VIP tier only when `wp_get_environment_type()` is `local` (set `WP_ENVIRONMENT_TYPE=local`). WordPress reports `production` when nothing is set, so they are refused by default (#5999).
- A forthexp checkout whose buyer matches no WordPress user no longer mints its `xp_live_` key onto user 1 (#5999). The route guard authenticates a key's requests as its owner, so those keys acted as the administrator. The key is now minted unowned (`user_id` 0) with the customer email in its new `owner_email` field, and the webhook id and key id are logged. The customer email is also read from `customer_details.email` when `customer_email` is empty. Revoke any `forthexp.com SaaS Key` owned by user 1 that the administrator did not buy.

## [1.0.0] - 2026-09-13

### Added
- Initial release of Xophz Gatekeeper as a COMPASS companion plugin submodule.
- Core plugin class `Xophz_Compass_Gatekeeper` extending `Xophz_Compass_Plugin_Base`.
- Machine-to-machine API key authority in `Gatekeeper_Keys` supporting customizable key prefixes (defaulting to `stargate_`) and granular capability scopes.
- Software license authority in `Gatekeeper_Licenses` supporting `CX-ST-` (flat-rate eBook), `CX-SP-` (GitHub Sponsor), and `CX-VIP-` keys with device activation limits.
- Entitlement registry in `Gatekeeper_Entitlements` tracking active GitHub Sponsors across Solo, Team Power Puff, and Enterprise tiers.
- Standardized REST controller `Gatekeeper_REST` under `compass/v1/gatekeeper` extending `Xophz_Compass_REST_Controller`.
- Admin management dashboard in `Xophz_Compass_Gatekeeper_Admin`.
- Wizard logo assets (`icon.png`, `icon.svg`).
